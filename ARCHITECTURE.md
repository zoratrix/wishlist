## 1. Резюме для заказчика

Мы делаем **веб-сервис вишлистов**: человек регистрируется, создаёт списки
желаний, делится ссылкой, а гости бронируют подарки **без регистрации** — в два
поля и одну кнопку. Владелец по умолчанию не видит, что уже забронировано.

Решение — **одно небольшое приложение**: сайт на React, сервер на Node.js, база
— файл SQLite. Запускается одной командой на вашем Windows-компьютере,
переносится копированием папки, публикуется на недорогом сервере в России.

| Параметр | Значение |
|---|---|
| Язык программирования | TypeScript (один язык и на сайте, и на сервере) |
| Что установить на компьютер | Node.js LTS (база данных и почта не требуют установки) |
| База данных | SQLite — файл `app.db` внутри папки проекта |
| Телефон | интерфейс проектируется сначала для телефона (Mobile First) |
| Расходы при разработке | 0 ₽ |
| Расходы после публикации | ~650–1 300 ₽/мес за сервер + ~399 ₽/год за домен |
| Открытие MVP | этапы 1–2; ориентировочно 5–8 рабочих сессий |
| Внешние сервисы | Яндекс ID (этап 5), почтовый сервис (этап 4), хостинг (этап 7) |

## 3. Технологический стек

| Слой | Технология | Простыми словами |
|---|---|---|
| Сервер | **Node.js 24 LTS + TypeScript + Express 5** | Программа, которая принимает запросы сайта и отвечает данными. TypeScript ловит часть ошибок до запуска. В разработке TypeScript исполняется Node.js напрямую — отдельная сборка не нужна. |
| Режим разработки | **Vite как middleware внутри Express** | Один процесс и один адрес `http://localhost:3000`: и сайт, и API. Отдельный порт и прокси не нужны. |
| База данных | **SQLite (WAL), файл `server/data/app.db`** | Вся база — один файл внутри проекта. Не нужен отдельный сервер БД, резервная копия — копия файла. |
| Работа с базой | **better-sqlite3** (prepared statements), миграции — SQL-файлы | Быстрый и предсказуемый драйвер без лишнего слоя; миграции — понятные SQL-файлы, которые легко прочитать. |
| Сайт | **React 19 + Vite + React Router 7 + TanStack Query + Tailwind CSS 4** | Интерфейс в браузере: быстрый, без перезагрузок, адаптивный. |
| Валидация | **Zod** | Единые правила проверки данных на сервере. |
| Пароли | **Argon2id** (`@node-rs/argon2`) | Современный стандарт; пароль в открытом виде не хранится. Пакет ставится без компилятора. |
| Сессии | своя таблица сессий + httpOnly cookie | Вход подтверждается cookie, нечитаемой из JavaScript. |
| Почта | **Nodemailer**; локально — **Mailpit**, в интернете — Яндекс Cloud Postbox / Unisender | Локально письма видно в «почтовом ящике» на экране; реальным людям ничего не уходит. |
| Картинки | **Multer + Sharp** | Загрузка с проверкой типа по содержимому, обрезка, удаление метаданных (в т.ч. GPS-координат). |
| Планировщик | внутри процесса сервера + очередь писем в БД | Раз в час проверяет напоминания; уникальные ключи не дают отправить дважды. |
| Тесты | **Vitest + Supertest**; Playwright — на этапе 6 по согласованию | Автопроверка сценариев, включая одновременное бронирование. |
| Публикация | **VPS в РФ + Caddy** | Caddy сам получает и продлевает бесплатный HTTPS-сертификат. |
| Версии | **Git** + точные версии зависимостей + `package-lock.json` | Воспроизводимая сборка; агентские файлы в Git не попадают (раздел 19). |

### 3.1. Почему не Prisma и не «модные» ORM

При проверке актуального состояния (ноябрь 2026) выяснилось: Prisma 7/8 перешли
на обязательные драйверы и ESM, а у её SQLite-адаптера недавно был дефект с
потерей записи при занятой базе — ровно на том участке, где у нас критична
целостность броней. Drizzle v1 находится в бете. Поэтому выбран
**Kysely + better-sqlite3**: стабильный типизированный построитель запросов,
никакой генерации кода и «магии», транзакции синхронные и предсказуемые.

### 3.2. Версии зависимостей

Все зависимости фиксируются **точными версиями** (без `^`), `package-lock.json`
хранится в репозитории, версия Node указана в `package.json` (`engines`) и
`.nvmrc`. Причина: проект должен собираться одинаково и сегодня, и после
переноса на другой компьютер через полгода.

## 4. Почему этот стек подходит (по критериям ТЗ)

| Критерий | Как выполняется |
|---|---|
| Простота разработки и поддержки | Один язык (TypeScript); один процесс; SQL-миграции читаемы; код разбит по модулям. |
| Запуск на Windows | Нужен только Node.js (уже установлен: v24.21). База — файл, почта — Mailpit (один `.exe`). |
| Перенос на другой компьютер | Копируется папка: код, `app.db`, `uploads/`, документация. `node_modules` восстанавливается `npm install`. |
| Публикация в интернете | Один процесс на одном порту; Caddy; скрипт установки; путь роста до PostgreSQL и объектного хранилища без переписывания сайта. |
| Низкая стоимость | Разработка 0 ₽; сервер ~650–1 300 ₽/мес; домен ~399 ₽/год; почта — бесплатный тариф до 2 000 писем/мес. |
| Надёжность данных | SQLite (WAL), внешние ключи, уникальные индексы, транзакции; ежедневный бэкап; база и файлы копируются вместе. |
| Адаптивные интерфейсы | Mobile First, проверка на 320–1440 px, крупные кнопки, компактный мобильный редактор. |
| Расширяемость | Смена базы (PostgreSQL) — переписать слой доступа к данным, логика и интерфейс не меняются; API разделён по модулям; новые функции добавляются точечно. |

Осознанный размен: **SQLite пишет в базу последовательно** (один писатель). Для
вишлистов этого достаточно с запасом (сотни одновременно работающих
пользователей). Взамен — нулевая настройка БД, надёжные бэкапы и переносимость.
Переход на PostgreSQL при росте — отдельная задача примерно на день работы, без
переписывания интерфейса.

## 5. Сравнение с альтернативами

| Вариант | Плюсы | Минусы | Вывод |
|---|---|---|---|
| **Next.js (full-stack) + PostgreSQL** | Один фреймворк, серверный рендеринг, простая публикация на Vercel | Смешаны серверный и клиентский код; на Vercel нет постоянного диска (SQLite не подходит), нужны внешние БД и хранилище; локально часто нужен Docker | Не выбран: больше «магии» и внешних сервисов, чем нужно |
| **Django + PostgreSQL (Python)** | «Всё в комплекте»: админка, права, безопасность по умолчанию | Второй язык; мобильный интерфейс всё равно на JS; установка PostgreSQL на Windows — лишний барьер для новичка | Сильный запасной вариант |
| **Laravel (PHP) + MySQL** | Дешёвый хостинг, много готового | PHP; интерфейс-«приложение» сложнее; на Windows нужен локальный веб-сервер | Отклонён |
| **Node + React + PostgreSQL** | Привычный «взрослый» стек | Нужно ставить PostgreSQL на Windows, помнить пароль, создавать БД — больше шагов, где новичок застревает | Заменён на SQLite, путь перехода сохранён |
| **Supabase / Firebase** | Быстрый старт, готовая авторизация | Привязка к коммерческому сервису и тарифам; данные вне вашего контроля; сложнее гарантировать атомарность и приватность | Отклонён (ТЗ: не привязываться к коммерческому сервису) |
| **Конструкторы (Tilda, Notion)** | Бесплатно и быстро | Невозможны атомарное бронирование, скрытие данных от владельца, подписки, уведомления | Не подходит по сути задачи |

**Почему React, а не серверные шаблоны (Django/HTMX):** нужен «живой» редактор
таблицы (мгновенное добавление строк, правка на месте, перетаскивание,
фильтры). На React это делается естественно; на шаблонах потребовалось бы много
ручного JavaScript.

## 6. Архитектура

### 6.1. Схема

```
       Телефон / планшет / компьютер
                    │ HTTPS
                    ▼
      ┌─────────────────────────────────────────────┐
      │ Caddy (в интернете) / Vite middleware (локально)
      ├─────────────────────────────────────────────┤
      │ Один процесс Node.js: Express + TypeScript  │
      │                                             │
      │  • REST API /api/...                        │
      │  • сессии, CSRF, лимиты запросов            │
      │  • проверка прав и приватности              │
      │  • атомарное бронирование                   │
      │  • раздача сайта (React) и /uploads         │
      │  • планировщик уведомлений                  │
      └───────┬──────────────────────┬──────────────┘
              │ Kysely               │ Nodemailer / fetch
     ┌────────▼─────────┐   ┌────────▼──────────────┐
     │ SQLite (WAL)     │   │ SMTP: Mailpit (локально)│
     │ server/data/     │   │       Postbox/Unisender │
     │ app.db           │   └───────────────────────┘
     └──────────────────┘   ┌───────────────────────┐
     ┌──────────────────┐   │ Яндекс ID (OAuth)     │
     │ uploads/         │   └───────────────────────┘
     │ аватары, обложки │   ┌───────────────────────┐
     └──────────────────┘   │ Внешние страницы      │
                            │ (Open Graph)          │
                            └───────────────────────┘
```

### 6.2. Взаимодействие компонентов

1. **Браузер** загружает сайт (React) и общается с сервером только через
   `/api/...` (JSON).
2. Один процесс. В интернете **Caddy** принимает HTTPS и передаёт запросы
   приложению. Локально тот же процесс содержит Vite и отдаёт сайт с мгновенными
   обновлениями, API — на том же адресе `http://localhost:3000`. В production
   сервер отдаёт собранный сайт; публикация — один процесс на одном порту.
3. **Сервер** на каждый запрос: проверяет сессию и CSRF → проверяет права и
   приватность (гость / подписчик / владелец) → валидирует данные (Zod) →
   работает с базой → собирает ответ **только из разрешённых полей**.
4. **Планировщик** раз в час запускает проверку напоминаний и отправку очереди
   писем. Уникальные ключи в базе не дают отправить одно письмо дважды даже
   после перезапуска.
5. **Файлы** лежат на диске в `uploads/`; имя генерирует сервер; тип проверяется
   по содержимому.

### 6.3. Почему один процесс, а не микросервисы

Проект обслуживает один владелец данных, который сам публикует и обновляет
сайт. Разделение на сервисы добавило бы второй порт, CORS, Nginx, ещё один
способ сломаться — без выигрыша. Один процесс проще запускать, отлаживать и
переносить.

## 7. Хранение данных

Подробно — [docs/DATABASE.md](docs/DATABASE.md). Кратко:

- **15 таблиц данных** (+ служебная `schema_migrations`): пользователи,
  сессии, токены писем, настройки, подписки, вишлисты, подарки, ссылки на товар,
  категории, брони, журнал попыток, уведомления, очередь писем, привязка
  Яндекс ID.
- **Главный инвариант**: у подарка не может быть **двух активных броней**.
  Гарантия — уникальный индекс в базе + синхронная транзакция. Одновременные
  запросы физически не смогут создать вторую бронь.
- **Отмена** не удаляет запись: проставляется время отмены — история
  сохраняется, подарок снова доступен.
- **Резервные копии**: `npm run db:backup` (безопасный снимок `VACUUM INTO`);
  на сервере — ежедневный автобэкап и копия в объектное хранилище (по желанию).
- **Смена базы на PostgreSQL** при росте: меняется слой доступа к данным
  (prepared statements → драйвер PostgreSQL); логика, API и интерфейс остаются.
- Даты хранятся в UTC в текстовом формате ISO 8601, поэтому базу можно открыть
  любым просмотрщиком и прочитать глазами. Дни рождения — отдельные
  целочисленные поля месяц/день/год.

## 8. API — принципы

Полное описание — [docs/API.md](docs/API.md). Ключевое:

- REST, JSON, префикс `/api`. Сессионная cookie (`HttpOnly`, `SameSite=Lax`,
  `Secure` в production) + CSRF-токен, привязанный к сессии.
- **Приватность на уровне сервера**: набор полей ответа различается для гостя,
  подписчика и владельца. Если владелец скрыл бронирования, сервер не отправляет
  ему ни одного поля о бронях — утечка через API или исходный код страницы
  невозможна.
- **Бронирование**: синхронная транзакция «проверка → вставка» + уникальный
  индекс. Гонка двух запросов → второй получает `409` и сообщение «Подарок уже
  забронировали».
- **Отмена**: сравнение нормализованного email (trim + регистр) в константном
  времени; неверный email → нейтральное сообщение; попытки журналируются и
  ограничиваются по частоте.
- **Email бронирующего** не возвращается никому и никогда.
- Ошибки — на русском, без технических подробностей и без раскрытия чужих
  данных.

## 9. Структура сайта

Подробно — [docs/UI.md](docs/UI.md). Кратко:

- Страницы: лендинг/вход, регистрация, подтверждение почты, сброс пароля,
  «Мои вишлисты», редактор, настройки списка, настройки профиля, уведомления,
  подписчики/подписки, публичный профиль `/u/:username`, публичный вишлист
  `/w/:token`, политика конфиденциальности, 404.
- Телефон: нижний таб-бар, большая кнопка «＋ Подарок», крупные кнопки.
- Два режима отображения: **«Таблица»** (по умолчанию) и **«Карточки»** — и в
  редакторе, и на публичной странице (выбор запоминается). Адаптивная ширина: до
  1440px на компьютере, формы уже; таблица во всю ширину, колонки
  пропорциональны. Колонки: №, Название, **Описание (≈30%, переносится)**,
  Приоритет, Цена, Ссылки, Статус, Действия — правка прямо в ячейках, строка
  добавления внизу (все поля сразу, Enter — добавить и продолжить). На телефоне
  компактные строки **без горизонтальной прокрутки**, добавление — формой со
  всеми полями.
- У подарка может быть **несколько ссылок** (до 10): маленькие квадратные
  кнопки-иконки с фирменным цветом/монограммой магазина (Ozon, WB, Я.Маркет и
  др.), нейтральные для неизвестных доменов; до 6 видно сразу, остальные — «＋N».
  Ссылки внутри описания автоматически становятся кликабельными.
- **Категории-теги** (0–5 у подарка, 20 на список) управляются в редакторе
  сверху, с **цветом из палитры 8 цветов** (без цвета — единый нейтральный вид);
  **сортировка** списка: порядок, время добавления, алфавит, цена, приоритет,
  категории, занятость. Сортировка/фильтр — клиентские; варианты «по занятости»
  скрыты владельцу при `showBooked=false` (иначе утечка броней).
- **Короткие ссылки на вишлист:** `shareToken` — 7 символов `[A-Za-z0-9]`
  (`/w/k7M2pQ9`); ранее выданные длинные токены продолжают работать.
- **Полное редактирование подарка — в модальном окне** (иконка-карандаш), все
  поля сразу, включая описание; сохранение одним PATCH.
- Гость видит свои брони: отметка «Забронировано вами» хранится в его браузере
  (localStorage), серверная приватность не меняется.
- Бронирование: кнопка → окно с двумя полями → одна кнопка подтверждения.
  Отмена: одно поле email → одна кнопка. Никаких регистраций и кодов.

## 10. Основные пользовательские сценарии

### 10.1. Гость бронирует подарок (главный сценарий)
1. Открывает ссылку `/w/<token>`, видит список.
2. Нажимает «Забронировать» у подарка.
3. Вводит имя и email, нажимает «Забронировать».
4. Видит «Готово! Подарок забронирован»; подарок помечается занятым для всех.
5. Может забронировать ещё подарки — без повторной регистрации.

### 10.2. Гость отменяет бронь
1. У занятого подарка нажимает «Отменить бронирование».
2. Вводит email, указанный при бронировании, подтверждает.
3. Совпало — бронь снимается сразу. Не совпало — нейтральное сообщение об
   ошибке. Писем и кодов нет.

### 10.3. Владелец создаёт список и вносит подарки
1. Регистрируется (email + пароль), при желании отключает письма.
2. Создаёт вишлист: название, описание, дата/повод, доступ.
3. Добавляет подарки: название + Enter → сразу следующий; при необходимости
   раскрывает строку и добавляет цену, ссылку, приоритет, категории.
4. Вставляет ссылку на товар — система пытается подставить название и картинку;
   если не получилось, заполняет вручную.
5. Делится ссылкой (кнопка «Поделиться» / копирование).

### 10.4. Владелец отмечает «уже подарен»
Раскрывает подарок, ставит статус «Уже подарен». Активная бронь закрывается
автоматически; подарок больше не предлагается к бронированию.

### 10.5. Подписка и напоминания (этапы 3–4)
1. Открывает `/u/<логин>`, нажимает «Подписаться» (если профиль публичный).
2. За месяц и за две недели до дня рождения подписчики получают уведомление на
   сайте и/или письмом — по настройкам.
3. Настройки уведомлений — в профиле; все письма отключаются одним
   переключателем.

### 10.6. Регистрация и восстановление доступа
Регистрация → письмо с подтверждением (локально видно в Mailpit) → мягкий
баннер, пока почта не подтверждена → «Забыли пароль?» → письмо со ссылкой →
новый пароль; старые сессии сбрасываются.

## 12. Локальная разработка

## 13. Публикация в интернете

Публикация — отдельный этап 7 с подробной инструкцией. Ниже — два варианта.

### 13.1. Вариант A — самый простой (рекомендуемый)

**Схема:** домен `.ru` → VPS в РФ (Москва) → наш скрипт установки → Caddy →
сайт с HTTPS.

Порядок для заказчика (после этапа 7 — с точными командами и скриншотами):
1. Зарегистрировать домен (например, на Timeweb — ~399 ₽/год).
2. Арендовать VPS с Ubuntu 24.04, 1–2 ГБ RAM (Timeweb — от 1 242 ₽/мес;
   Aeza — от €5,93/мес ≈ 600 ₽/мес, Москва/СПб; Beget — на момент проверки
   приём заказов был приостановлен).
3. Прописать A-запись домена на IP сервера (через панель регистратора).
4. Подключиться к серверу по SSH (инструкция для Windows: терминал или PuTTY).
5. Выполнить одну команду установки из нашего репозитория — она поставит
   Node.js, Caddy, создаст системную службу, настроит `.env`, применит миграции
   и ежедневный бэкап.
6. Открыть сайт по адресу `https://домен` — HTTPS выдастся автоматически.

Проверено по документации: Caddy выдаёт и продлевает сертификаты Let's Encrypt
автоматически ([caddyserver.com/docs/automatic-https](https://caddyserver.com/docs/automatic-https)).

### 13.2. Вариант B — гибкий, для роста

Тот же сервер, но с Docker Compose (приложение + Caddy + ежедневный бэкап).
Когда нагрузки станет больше: база переезжает на управляемый PostgreSQL
(Yandex Cloud), картинки — в Object Storage, появляется возможность запускать
несколько копий приложения. Стоимость растёт по мере необходимости, но
переездов «с нуля» не потребуется.

Зарубежные PaaS (Railway, Render, Fly.io) технически подходят, но требуют
зарубежной карты — для заказчика нецелесообразны.

### 13.4. Персональные данные и 152-ФЗ — отложено по решению заказчика

**Решение от 12.11.2026:** сервис создаётся для узкого круга (пара друзей) и не
будет публично распространяться. Поэтому уведомление РКН, политика обработки ПД
и юридическое оформление согласия **сейчас не делаются**.

Что при этом сохраняем в коде (это качество продукта, а не юридическое
требование):
- минимизация данных — не собираем ничего лишнего;
- удаление аккаунта реально удаляет данные;
- email бронирующих не видит никто, включая владельца;
- пароли и токены хранятся только в виде хешей.

Базовый чек-лист, если сервис когда-нибудь станет публичным (сохранён, чтобы не
потерять):
1. уведомление в Роскомнадзор (бесплатно, до начала обработки);
2. страница политики обработки ПД;
3. чекбокс согласия при регистрации;
4. хранение базы в РФ;
5. регламент уведомления об утечке (24 часа).

Это не заменяет консультацию юриста.

## 15. Тестирование

- **Автотесты (Vitest + Supertest)** — на каждый модуль: авторизация, права
  доступа, вишлисты, подарки, бронирование, отмена, уведомления.
- **Обязательные сценарии бронирования** (по ТЗ): один бронирует; второй
  получает отказ; **10 одновременных запросов → ровно одна бронь**; отмена
  своей; попытка отменить чужую; попытка повторной отмены; владелец не видит
  бронь; владелец включает показ броней; включает показ имён; посетитель не
  получает email; статус «подарен»; после «подарен» бронь невозможна.
- **Тесты приватности ответов API**: для каждого случая проверяется, что в JSON
  **отсутствуют** запрещённые поля (а не просто «скрыты» на клиенте).
- **Тесты прав доступа**: закрытый профиль, вишлист «только подписчикам»,
  чужой вишлист, чужие настройки, чужой экспорт.
- **Ручная проверка на телефоне** (по чек-листу этапа 6): 320/360/390/768 px,
  добавление подарков одной рукой, бронирование за несколько секунд.
- **Проверка восстановления**: остановить сервер, восстановить базу из бэкапа,
  запустить, убедиться, что данные и брони на месте.
- **Проверка безопасности**: лимиты, CSRF, попытки SQL-инъекций, XSS-строки в
  названиях подарков, загрузка файлов с подменой типа, SSRF-попытки в
  предпросмотре ссылки.

Ограничение честно фиксируем: 100% гарантии безопасности не существует ни у
одного сайта; мы закрываем классы атак из ТЗ и проверяем их тестами.

## 16. Риски и спорные моменты

| Риск | Влияние | Меры |
|---|---|---|
| Отмена брони по одному email — слабое подтверждение: знающий email может отменить чужую бронь | среднее | Это требование ТЗ. Меры: лимиты попыток, нейтральные ошибки, константное сравнение, журнал, запрет раскрытия email. Остаточный риск принимаем осознанно |
| Двойное бронирование при гонке | высокое | Уникальный индекс в БД + транзакция + тест с 10 одновременными запросами |
| Утечка броней владельцу через интерфейс/API | высокое | Серверные DTO, тесты на отсутствие полей; переключатели только расширяют набор данных |
| Prisma/ORM-зависимости, «модные» версии ломают совместимость | среднее | Выбран стабильный Kysely; точные версии + lock-файл; проверка обновлений отдельной задачей |
| Нативная сборка `better-sqlite3` на Windows (нет prebuilt под версию Node) | среднее | Проверяем на этапе 1 сразу; резерв — Node.js 22 LTS или встроенный `node:sqlite`. Переносный риск ограничен этапом 1 |
| Антибот маркетплейсов блокирует автозаполнение | среднее | Обещаем «попробуем»; ручной ввод — основной путь; не зависим от магазина |
| Письма попадают в спам (нужны SPF/DKIM/DMARC, свой домен) | среднее | Настройка домена по инструкции; Mailpit локально; тестовое письмо перед запуском |
| SQLite — один писатель | низкое при нашем масштабе | Короткие транзакции, WAL, `busy_timeout`; путь перехода на PostgreSQL описан |
| Потеря данных при переносе/поломке диска | высокое | Ежедневный бэкап на сервере + инструкция восстановления; копия базы в папке проекта |
| Windows ≠ Linux (регистр файлов, переводы строк) | среднее | `.gitattributes` с LF, файлы в нижнем регистре, тесты и сборка на сервере |
| Ошибки в датах: 29 февраля, граница года, часовые пояса | среднее | Отдельная политика (29.02 → 28.02 в невисокосные годы), тесты на эти даты |
| 152-ФЗ и РКН, если сервис станет публичным | отложено | Сейчас — для личного круга; чек-лист сохранён в разделе 13.4 |
| Объём проекта больше, чем кажется («сделать всё сразу») | высокое (сроки) | Поэтапный план, MVP сначала, функции этапа 5 — после проверки ядра |
| Зависимость от одного бесплатного почтового тарифа | низкое | Второй провайдер как замена, абстракция отправки в коде |

## 17. Противоречия и неоднозначности ТЗ — предлагаемые решения

| № | Вопрос | Предлагаемое решение | Нужно подтверждение |
|---|---|---|---|
| 1 | Владелец не видит брони, но должен ставить «уже подарен». Как он узнаёт? | Он узнаёт это в жизни (подарок вручили). Статус ставится вручную, активная бронь закрывается автоматически. Уведомлений владельцу о бронях не отправляем — это раскрыло бы факт брони | нет |
| 2 | Переключатели «показывать забронированные» — глобальные или на каждый вишлист? | На каждый вишлист (разные списки — разные ситуации) + значения по умолчанию в настройках профиля | да, желательно |
| 3 | При скрытых бронях — показывать ли владельцу счётчик «5 из 10 забронировано»? | Нет. Это косвенная утечка. Владелец видит нейтральный список | да |

## 19. Документация и перенос между компьютерами

### 19.1. Файлы в корне проекта

| Файл | Назначение |
|---|---|
| `README.md` | как запустить проект «с нуля» |
| `ARCHITECTURE.md` | этот документ |
| `docs/DATABASE.md`, `docs/API.md`, `docs/UI.md` | детальные проектные документы |
| `docs/RUN.md`, `docs/DEPLOY.md` | запуск и публикация (этапы 1 и 7) |
| `CONTEXT.md` | состояние проекта для продолжения работы |
| `AGENTS.md` | правила для AI-агента (стиль, команды, запреты) |
| `TODO.md` | задачи: сделано / в работе / далее / отложено / проблемы |
| `CHANGELOG.md` | история изменений с датами |
| `.env.example` | пример переменных окружения без секретов |
| `.gitignore` | что не попадает в Git |

### 19.2. Git и изоляция агентских файлов

В Git попадают: исходный код, конфигурация сборки, миграции, тесты,
пользовательская документация, README.

Не попадают (перечислены в `.gitignore`, проверяется перед каждым коммитом):
`CONTEXT.md`, `AGENTS.md`, `TODO.md`, `prompt.md`, папка `agent/`, `.env`,
`node_modules/`, `server/data/*.db`, `uploads/`, `backups/`, логи, сборки.
Правило: перед коммитом смотрим список файлов (`git status --short`), секреты и
агентские файлы не добавляем. Проверка делается и вручную, и скриптом.

### 19.3. Перенос на другой компьютер

1. Скопировать **всю папку проекта** (флешка/внешний диск).
2. Установить Node.js LTS.
3. В папке выполнить `npm install`.
4. Скопировать `.env.example` → `.env` и заполнить (для локальной работы
   достаточно значений по умолчанию из примера).
5. Запустить `npm run dev`. База уже внутри папки — данные на месте.

**Нельзя потерять:** `server/data/app.db`, папку `uploads/`, `.env`,
документацию. **Можно восстановить:** `node_modules`, сборки, логи, кэши.
