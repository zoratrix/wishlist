# API — общее описание

> **Актуальный контракт этапа 2 (MVP) — `docs/API-CONTRACT-MVP.md`.** При
> расхождении этого документа с контрактом MVP приоритет у контракта: там
> перечислены точные поля запросов и ответов, реализованные в коде.

Базовый префикс: `/api`. Формат — JSON (кроме загрузки файлов и экспорта).
Все проверки прав и приватности выполняются **на сервере**; клиент не является
источником истины.

## 1. Общие соглашения

### 1.1. Аутентификация
- Сессионная cookie `sid`: `HttpOnly`, `SameSite=Lax`, `Secure` в production,
  срок 30 дней со скользящим продлением.
- Токен сессии хранится в БД только в виде SHA-256 хеша.
- Пароли — Argon2id. Сессия не хранит пароль.

### 1.2. CSRF
- Cookie сессии: `HttpOnly`, `SameSite=Lax`, `Secure` в production, с префиксом
  `__Host-`. Никаких изменяющих состояние `GET`-запросов. CORS не разрешён
  (сайт и API на одном адресе).
- Основная защита: `SameSite=Lax` + проверка `Origin` (с запасным вариантом
  `Sec-Fetch-Site`) для всех `POST`/`PATCH`/`DELETE`; несовпадение → `403`.
- Второй слой: **токен, привязанный к сессии** (synchronizer token). Сервер
  хранит `csrf_token` в записи сессии и отдаёт его в `GET /api/auth/me`; клиент
  присылает `X-CSRF-Token`, сервер сравнивает с сохранённым. Это сильнее
  «наивного» double-submit, который OWASP не рекомендует как единственную
  защиту.
- Токен обновляется при входе (новая сессия).

### 1.3. Ограничение частоты и защита от автоматических регистраций
Лимиты в памяти процесса (кроме отмены брони — см. `BookingAttempt`):

| Действие | Лимит |
|---|---|
| Вход | 10 попыток / 15 мин на IP+email |
| Регистрация | 5 / час на IP |
| Письма (подтверждение, сброс) | 3 / час на пользователя, 10 / час на IP |
| Сброс пароля | 5 / час на IP |
| Бронирование | 30 / час на IP |
| Отмена брони | 10 / час на подарок, 30 / час на IP (в БД) |
| Предпросмотр ссылки (OG) | 20 / час на пользователя |
| Загрузка изображений | 30 / час на пользователя |

Ответ `429` с полем `retryAfter` (секунды) и понятным русским текстом.

Защита от автоматических регистраций: лимит по IP + **скрытое поле-ловушка**
(honeypot: если браузер заполнил невидимое поле — регистрация отклоняется) +
подтверждение email, которое делает массовую регистрацию бессмысленной. Если
появится реальный спам — добавим Яндекс SmartCaptcha (этап 6, по согласованию).
Пароли проверяются на минимальную длину 8 символов и наличие в списке самых
распространённых (отказ с понятным текстом).

### 1.4. Формат ошибок
```json
{ "error": { "code": "GIFT_ALREADY_BOOKED",
             "message": "Этот подарок уже забронировали.",
             "details": null } }
```
- Сообщения на русском, без технических деталей и без раскрытия чужих данных.
- Ошибки валидации: `code: "VALIDATION_ERROR"`, `details` — список полей.

### 1.5. Коды ответов
`200/201` — успех, `204` — успех без тела, `400` — неверные данные,
`401` — не залогинен, `403` — нет прав, `404` — не найдено/скрыто,
`409` — конфликт (уже забронировано), `422` — бизнес-правило нарушено,
`429` — слишком часто.

аккаунту **только после подтверждения паролем** (защита от захвата аккаунта);
если пароля нет (аккаунт создан через Яндекс) — вход сразу.

## 7. Публичный вишлист и бронирование (без регистрации)

| Метод | Путь | Доступ | Описание |
|---|---|---|---|
| GET | `/api/w/:shareToken` | гость / по правилам видимости | `{ wishlist, gifts, categories, viewer }` — вишлист глазами посетителя |
| POST | `/api/w/:shareToken/gifts/:giftId/book` | гость | тело: `{ name, email }` |
| POST | `/api/w/:shareToken/gifts/:giftId/unbook` | гость | тело: `{ email }` |
| POST | `/api/metadata/preview` | авторизованный | `{ url }` → название/картинка/цена по Open Graph |

`viewer` — отношение смотрящего к **владельцу списка**:
`{ isSelf, isFollowing, canFollow }`, правила те же, что у `viewer` в
`GET /api/users/:username` (см. п. 4). Гость → всё `false`; владелец →
`isSelf: true`; профиль владельца закрыт → `canFollow: false` (сам список при
этом может быть доступен по ссылке). Поле нужно клиенту, чтобы показать в шапке
вишлиста кнопки «Профиль» и «Подписаться»; никаких чужих данных оно не раскрывает.

### 7.1. Бронирование — детали
1. Проверка доступа к вишлисту (видимость/токен).
2. Проверка: подарок существует, `status = available`, активной брони нет.
3. Валидация: имя 1–100 символов, email по формату, нормализация email
   (trim + lowercase).
4. Транзакция: вставка `Booking`. Гонка → `P2002` → **409**.
5. Ответ: `201 { booking: { createdAt } }` + сообщение «Подарок забронирован»,
   **без email и без id брони в ответе**.
6. Повторные бронирования тем же email на другие подарки разрешены всегда.
7. Письмо посетителю **не отправляется** (по ТЗ — никаких подтверждений).

### 7.2. Отмена — детали
1. Найти активную бронь подарка. Если нет → `404` (одинаковый ответ для «нет
   брони» и «бронь не ваша»).
2. Сравнить нормализованный email **константное время** (`crypto.timingSafeEqual`
   по хешам). Несовпадение → `400` с текстом «Не удалось отменить бронирование.
   Проверьте email, который указывали при бронировании.» — без раскрытия
   сохранённого адреса.
3. Успех → `cancelledAt`, `cancelledReason = visitor`, `200`.
4. Каждая попытка пишется в `BookingAttempt`; превышение лимита → `429`.
5. Письма не отправляются.

### 7.3. Что посетитель видит про занятые подарки
- `booking: { status: "booked" }` — и ничего больше. Без имени, email, времени.
- Кнопка «Забронировать» заменена на «Занят» с возможностью открыть окно
  отмены (кнопка «Это я, отменить бронирование»).
- Если владелец включил «показывать, кто забронировал» — это касается **только
  владельца**, посетители имён всё равно не видят.

## 10. Загрузка файлов

- `multipart/form-data`, поле `file`.
- Белый список типов: `image/jpeg`, `image/png`, `image/webp`; проверка **по
  содержимому** (магические байты), а не по расширению.
- Лимит 5 МБ; ресайз через `sharp` (аватар 400×400, обложка 1200×600, картинка
  подарка 800×800), пересохранение без метаданных (EXIF-геолокация удаляется).
- Имя файла генерируется сервером (случайный id + расширение) — защита от
  path traversal и перезаписи.
- Раздача: `/uploads/...` с `Content-Type` из белого списка,
  `X-Content-Type-Options: nosniff`, `Cache-Control: public, max-age=31536000`
  (имена неизменяемые).

## 11. Предпросмотр по ссылке (Open Graph) — детали безопасности

Реализация: собственный `fetch` (undici) + разбор HTML через `cheerio`.
Готовая библиотека `open-graph-scraper` не используется: она сама ходит в сеть,
и проконтролировать SSRF в ней сложнее.

- Схема только `http`/`https`, порты только 80/443; запрет `file:`, `ftp:`,
  `localhost`, IP-адресов и частных диапазонов (`127.0.0.0/8`, `10/8`,
  `172.16/12`, `192.168/16`, `169.254/16`, `169.254.169.254`, `::1`,
  `fc00::/7`, multicast) — защита от SSRF.
- DNS резолвится **до** соединения; проверяются **все** полученные адреса
  A/AAAA; соединение выполняется на уже проверенный IP (защита от DNS
  rebinding через собственный `lookup` у undici-агента).
- Редиректы: не более 3, каждый хоп проверяется заново по тем же правилам.
- Таймаут 4 с на весь запрос, максимум 1 МБ тела, обязательный
  `Content-Type: text/html`, понятный User-Agent, без cookies и без
  авторизации.
- Ограничение частоты: 20 запросов в час на пользователя.
- Если данные получить не удалось (антибот магазина, отсутствие Open Graph) —
  ответ `200 { ok: false, reason: "..." }`, а не ошибка: пользователь заполняет
  поля вручную. Платформа не зависит от конкретного магазина.
- Реальность: Ozon, Wildberries и Яндекс Маркет активно противодействуют
  автоматическим запросам и могут отвечать `403`/капчей. Поэтому автозаполнение
  честно позиционируется как **вспомогательное**: основной путь — ручной ввод.
  Полученные данные кэшируются, повторные запросы к той же ссылке не выполняются.

## 12. Экспорт

- `GET /api/me/wishlists/:id/export?format=csv` — CSV, разделитель `;`
  (совместим с русской локалью Excel), UTF-8 с BOM.
- Колонки: №, Название, Описание, Ссылка, Цена, Валюта, Приоритет, Категории,
  Статус.
- Статус бронирования попадает в экспорт **только** если владелец включил
  `showBooked` (иначе экспорт не должен раскрывать то, что скрыто в интерфейсе).
- Данные бронирующих (имя/email) в обычный экспорт не попадают никогда.
- Excel (.xlsx) — тот же файл утилитой `exceljs` под тем же правилом (этап 5).
